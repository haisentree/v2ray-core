> 走读时间：2026-10-22

## 一、与入站侧的结构对偶

| | inbound（07 课） | outbound（本课） |
|---|---|---|
| 层级 | Manager → Handler(AlwaysOn/Dynamic) → **N workers** | Manager → **Handler 单层** |
| 驱动方式 | 被动：listener accept 驱动 | 主动：Dispatch 调用驱动 |
| 连接来源 | 内核递进来的 conn | 自己 Dial 出来的 conn |
| proxy 调用 | `Process(ctx, network, conn, dispatcher)` | `Process(ctx, link, handler 兼任 Dialer)` |
| UDP | udpWorker 用 connID 模拟会话 | packetaddr 分支 / 协议自理 |
| mux | mux.Server 挡在前面（服务端） | mux.ClientManager 可选（客户端） |
| stats | conn 装饰（Read=downlink） | conn 装饰（Write=uplink，方向翻转） |

**为什么不需要 worker 层**：入站要"守着端口等连接"，出站"每次 Dispatch 现场拨号"——没有监听就没有 worker 的存在意义。这是被动/主动语义差在结构上的投影。

## 三、Dial 决策链（handler.go:196，见上图）★ 本课核心

proxy 协议层（freedom 等）调 `dialer.Dial(ctx, dest)` 时，Handler 按顺序过五关：

```
① 链式代理：proxySettings.tag 非空
   → ohm.GetHandler(tag) 拿到上游 handler
   → 再造一对 pipe，go handler.Dispatch(ctx, link)
   → 把 (uplinkWriter, downlinkReader) 包装成 net.Connection 返回！
   → 之后照样可以叠 security engine（TLS over 代理链）
   ★ v2ray 链式代理的完整实现：一个 Dial 变成一次内部 Dispatch

② TransportLayerProxy（tun 场景）：ctx 打标 → internet 层 DialTaggedOutbound

③ packetaddr（UDP 特例）：本地 UDP socket 包装成 PacketAddrConn

④ 默认路径的准备动作（senderSettings 非空时）：
   Via → outbound.Gateway（绑源地址）
   DomainStrategy → 挂 outbound.Resolver（04 课 DialSystem 消费）

⑤ internet.Dial(ctx, dest, h.streamSettings) → 04 课 dialer 注册表
⑥ getStatCounterConnection 装饰后返回
```

**链式代理与 sniffing 的对称美**：入站侧"数据经 pipe 到 dispatcher"（08 课番外），出站侧"数据经 pipe 到上游 handler"——同一个 pipe 机制支撑两个方向的解耦。

## 四、Dispatch（handler.go:153）

```
① senderSettings.DomainStrategy ≠ AS_IS 且目标有域名 → 先解析成 IP
② mux 启用（或 ctx 要求）→ h.mux.Dispatch(ctx, link)  ← 连接复用
③ 否则 h.proxy.Process(ctx, link, h)                   ← 02 课那行
错误惯例：SubmitOutboundErrorToOriginator 把错误传回发起方（dokodemo 回写客户端）
        + Interrupt link.Writer / link.Reader 收尾
```

注意 ① 在 proxy.Process **之前**把域名换成 IP——而 freedom 自己的 useIP 是协议内部行为；两层解析点语义不同（handler 层=出站配置强制，protocol 层=协议配置可选）。

## 五、两课合璧的心智模型

```
入站：listener 守门 → callback 包装 ctx → proxy.Process（协议解析，还原目标）
                                                    │ Dispatch(ctx, dest)
出站：Handler.Dispatch → proxy.Process（协议加密，封装目标）→ handler.Dial → 内核
```

一进一出，`session.Outbound.Target` 是贯穿全程的接力棒；嗅探可能中途改写它，路由依据它选 handler，协议层加密它，Dial 层实现它。

## 自测

1. 为什么出站侧不需要"worker 模拟 UDP 会话"？
   （答：出站连接由 Dispatch 主动发起，一次 Dispatch 本身就是"一个逻辑会话"；UDP 的会话语义由发起方（dispatcher/udp dispatcher）维护，出站 handler 只需在 Dial 里给出可写的 conn。）
2. 链式代理里，TLS 加在哪一跳？
   （答：`securityEngine.Client(conn)` 包在"由上游 handler 递归 Dispatch 得到的 conn"外面——即外层协议（如 vmess over WS+TLS）加密的是整个链路的承载段；内层协议的加密在上游 handler 的 proxy.Process 里完成，两层互不知晓。）
3. `SubmitOutboundErrorToOriginator` 给谁用？
   （答：dokodemo 类入站会把"错误回传函数"放进 ctx（session.Originator），出站失败时回写客户端（如回 SOCKS 通用失败应答），而不是默默断链。）
