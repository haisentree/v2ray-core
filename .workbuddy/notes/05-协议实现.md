# 05 - 进阶（上）：vmess 与 trojan 加密协议实现

> 走读时间：2026-10-22
> 涉及文件：`proxy/trojan/protocol.go` / `client.go` / `validator.go`；`proxy/vmess/outbound/outbound.go`；`proxy/vmess/encoding/client.go` / `auth.go`
> 场景延续：02 课 Step 6——出站协议拿到的 `link + dialer`，本课看它们往 conn 里写什么

## 一、trojan：最简协议（protocol.go:71 writeHeader）

```
[56 字节 hex(SHA224(password))] CRLF [1B cmd: TCP=1/UDP=3] [目标地址端口] CRLF [payload...]
```

四个设计决策：
1. **密码不直接传**：SHA224 → hex 小写 56 字节。服务端 validator（validator.go）只存 hash，比对 O(1)，密码不落盘明文比较。
2. **自己不加密，全靠外层 TLS**：裸传 hash 的前提是 TLS 已保护信道。这是 trojan 的灵魂——**流量在审查者眼里就是标准 HTTPS 会话**（证书 SNI 是真实网站时更难分辨）。
3. **UDP 多一层封装**（writePacket:146）：`addr + len(2B) + CRLF + payload`，同一 TCP 连接上复用。
4. **抗时序探测**：`headerSent` 懒发送 + 客户端 `CopyOnceTimeout(FirstPayloadTimeout)`（client.go:149）——有首包就把 header+payload 一次 flush，没有就等首包再发。首字节时序和"header 单独成包"都是 TLS-in-TLS 探测的特征，这里刻意抹平。

服务端复用同一个 `ConnReader.ParseHeader`（protocol.go:197）按定长字段读回。

## 二、vmess：单包认证的教科书（encoding/client.go:86）

### 请求头构成（明文，随后整体加密）

```
Version(1) + requestBodyIV(16) + requestBodyKey(16) + responseHeader(1)
+ Option(1) + [paddingLen<<4 | security](1) + 保留(1) + Command(1)
+ 目标地址端口 + 随机 padding(0~15) + FNV1a 校验(4)
```

### 认证：hash(H + timestamp) —— 无状态、无握手

```go
timestamp := NewTimestampGenerator(NowTime, 30)   // 当前时间 ±30s 随机
idHash := hash(UUID)                              // 16B 用户 hash
idHash.Write(uint64(timestamp))                   // 追加时间戳再 hash
writer.Write(idHash.Sum(nil))                     // 16B 放头部最前面（legacy 模式）
```

服务端 `TimedUserValidator` 对每个 UUID 维护**最近 ±90s 的时间戳 hash 表**：收到连接只查表，O(1) 确认用户。**认证信息内嵌在第一个包里，无需任何握手往返**。时间戳窗口 = 防重放（捕获的密文 90s 后失效）。

### 请求头加密（两种模式）

| 模式 | 加密 | 密钥来源 |
|------|------|---------|
| legacy（有 AlterID） | AES-128-CFB | Key=UUID.CmdKey；IV=hashTimestamp(md5, timestamp)——**时间戳锁进 IV**，服务端能解密即隐含验证时间 |
| AEAD（默认，AlterID==0） | AES-GCM（KDF 链派生子密钥） | `vmessaead.SealVMessAEADHeader(cmdKey, header)` |

### body 密钥协商：不用 DH，靠加密头分发

- 客户端随机生成 `requestBodyKey/IV`（client.go:60），**放进加密的请求头**传给服务端；
- 响应方向 key = `sha256(requestKey)[:16]`（AEAD）/ `md5(requestKey)`（legacy），**双向密钥分离**；
- 没有前向保密——这正是"vmess 必须套 TLS"的另一个理由。

### body 编码（EncodeRequestBody:140）

chunk 流格式：`[size(2B)] [padding] [AEAD 密文]`，nonce 随 chunk 序号递增：
- `ChunkMasking`：**Shake128 流对 size 字段做 mask**（auth.go:79 ShakeSizeParser）——同长度的包 size 字段也不同，抗流量指纹；
- `GlobalPadding` / `AuthenticatedLength`：随机填充，抗长度侧信道；
- security 可选 NONE / LEGACY(AES-CFB) / AES128_GCM / CHACHA20_POLY1305 / ZERO。

### 抗主动探测的隐藏机关：behaviorSeed drainer

`outbound.go:133`：`HMAC-SHA256("VMessBF", UUID)` → CRC64 → `drain.NewBehaviorSeedLimitedDrainer(behaviorSeed, 18, 3266, 64)`。

认证失败时，服务端**按这个种子决定"读掉多少字节再断开"**——使攻击者无法从断开时机的分布区分"用户不存在 / 密码错误 / 时间戳过期"。用确定性噪声抹平错误信号，非常巧妙。

## 三、vmess vs trojan 对比表

| | vmess | trojan |
|---|-------|--------|
| 认证 | hash(UUID+时间戳)，±90s 防重放 | hash(SHA224 密码) 前缀比对 |
| 加密 | 内建（AES-GCM/ChaCha20 chunk 流） | **无，依赖外层 TLS** |
| 握手 | 无（单包认证） | 无（首包即认证） |
| 流量形态 | 自定义二进制（需靠 padding/masking 掩护） | 伪装成标准 HTTPS |
| 密钥协商 | 随机 bodyKey 经加密头分发 | TLS session key |
| 抗探测 | drainer 抹平错误信号、padding | 首包合并、真实证书 |

## 速记 + 自测

> **速记**：`trojan = hash 前缀 + 地址 + 靠 TLS 撑腰；vmess = 时间戳单包认证 + 加密头分发 body 密钥 + chunk 流 AEAD；两者都无握手、都靠"长得正常"活下来。`

1. 为什么 vmess legacy 模式把时间戳放进 AES-CFB 的 IV？
   （答：服务端必须用 hash(timestamp) 作 IV 才能解出头——解密成功本身即证明客户端知道当前时间窗，防重放不需要额外字段。）
2. trojan 服务端为什么存 hash 而不存明文密码？
   （答：比对只需 hash；配置文件泄露也不泄露可用凭据的明文形态（hex(SHA224) 即凭据本体，但比明文密码多一层），且查找 O(1)。）
3. 客户端连上 vmess 服务器但发一个随机 64 字节，服务端会立即断开吗？
   （答：不会立即断——先按 behaviorSeed drainer 读满预定字节数再断，抹平时序特征；这就是"drain"的含义。）
