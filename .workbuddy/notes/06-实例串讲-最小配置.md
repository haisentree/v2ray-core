> 时间：2026-10-22。用户给出的考题配置（log=debug，1 个 socks 入站关嗅探关 UDP，1 个 freedom 出站）

## 一、这份配置装配出什么（启动期）

`v4.Config.Build()`（infra/conf/v4/v2ray.go:373）翻译后，`initInstanceWithConfig`（v2ray.go:203）装配：

| 顺序 | 组件 | 类型 | 来源 |
|------|------|------|------|
| App[0] | app/log（debug 级） | Feature | JSON `log` 段（插队保证最先启动） |
| App[1] | app/dispatcher | Feature | **无条件硬编码** |
| App[2] | app/proxyman/inbound | Feature（Manager） | **无条件硬编码** |
| App[3] | app/proxyman/outbound | Feature（Manager） | **无条件硬编码** |
| 兜底 | localdns | Feature | 没配 `dns` 段 → v2ray.go:243 补默认 |
| 兜底 | policy.DefaultManager | Feature | 没配 `policy` 段 → :244 |
| 兜底 | **routing.DefaultRouter** | Feature | 没配 `routing` 段 → :245，**本例的关键角色** |
| 兜底 | stats.NoopManager | Feature | 没配 `stats` 段 → :246 |
| Handler | socks-in → proxy/socks Server | Handler | inbounds[0]，proxyman/inbound 领养 |
| Handler | direct → proxy/freedom Handler | Handler | outbounds[0]，**同时是默认出站**（App 列表第一个） |

与 demo 配置（01b）的差异：少了 dns/router 两个"配了才有"的 feature，换成了两个兜底实现——**行为差别只在路由决策一步**。

## 二、数据怎么流（运行期，对应上图）

```
curl --socks5 127.0.0.1:10808 http://example.com

① listener accept → inbound worker 造 session.Inbound{Source,Gateway} 入 ctx
   → socks.Server.Process（server.go:65）
② SOCKS5 握手（noauth 方法协商 → CONNECT 请求）→ dest = example.com:80
   handshakeFinalizingDispatcher 保证出站建立后才回"CONNECT succeeded"
③ dispatcher.Dispatch（default.go:203）
   - getLink 造 uplink/downlink 两根 pipe，返回 inboundLink
   - sniffing.enabled=false → 不起嗅探 goroutine，直接 go routedDispatch
④ routedDispatch（default.go:300）
   - 无 forced tag → d.router.PickRoute
   - DefaultRouter 零规则 → ErrNoClue（router.go:118 路径：domainStrategy 不是
     IpIfNonMatch、无规则可匹配）
   - handler=nil → GetDefaultHandler() → direct（freedom）
⑤ handler.Dispatch → freedom.Process（freedom.go:95）
   - dialer.Dial(example.com:80) → internet.Dial 查表 → tcp.Dial → DialSystem
   - requestDone/responseDone 双向 buf.Copy
⑥ 响应：远端 → conn → downlinkWriter → pipe → socks responseDone → 客户端
```

debug 级日志能亲眼看到的：`TCP Connect request to example.com:80`、`default route for ...`、`opening connection to example.com:80`——三句话正好对应 ③④⑤。

## 三、feature 之间怎么交互（本例的灵魂）

**答案：零直接引用。三种交互介质：**

1. **接口调用**——每个组件只认识 `features/` 里定义的接口：
   - socks 只认 `routing.Dispatcher`（Process 的第三个参数）
   - dispatcher 只认 `routing.Router` 和 `outbound.Manager`
   - freedom 只认 `internet.Dialer` + `transport.Link`
   - 替换任何一个实现（如 DefaultRouter → app/router），其他组件无感知。

2. **context 传值**——连接的元数据全程挂在 ctx 里漂流：
   - `session.Inbound`（来源/网关/用户，listener 造）
   - `session.Outbound`（目标，Dispatch 造）
   - `log.AccessMessage`（审计日志）
   - 不需要任何全局状态，天然并发安全。

3. **transport.Link（双管道）**——数据面唯一的传输介质：
   - socks 拿 inboundLink，freedom 拿 outboundLink，中间隔着两根内存 pipe
   - 两端素未谋面，却完成数据接力——这就是"任意入站 × 任意出站"的物理基础。

## 四、自测题（本例专属）

1. 把 `"sniffing": {"enabled": true}` 打开后，数据流哪一步会变化？
   （答：Dispatch 里多一个 goroutine 偷看首包嗅探 SNI/Host；若嗅到域名会改写 dest 再走路由。本例无 routing 规则，改写只影响日志和日志里 access message 的 To 字段，行为不变——因为最终还是默认出站。）
2. 如果把 outbounds 里加一个 `{tag:"proxy", protocol:"blackhole"}` 放在 direct 前面，会怎样？
   （答：默认出站 = App 列表第一个 = proxy（blackhole）——所有流量被吞。DefaultRouter ErrNoClue 后 GetDefaultHandler 拿的就是第一个，顺序即默认。）
3. udp:false 时 socks 的 UDP ASSOCIATE 请求会怎样？
   （答：Server.Network() 不含 UDP → listener 不监听 UDP；TCP 层收到 UDP ASSOCIATE 命令会回命令不支持，客户端 UDP 功能不可用，但 TCP 代理不受影响。）
