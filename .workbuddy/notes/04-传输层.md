# 04 - 传输层：dialer/listener 注册机制与 streamSettings

> 走读时间：2026-10-22
> 涉及文件：`transport/internet/dialer.go` / `tcp_hub.go` / `config.go` / `security/util.go` / `tcp/dialer.go` / `tcp/hub.go` / `tls/tls.go` / `system_dialer.go`
> 场景延续：02 课 Step 6 里 freedom 的 `dialer.Dial(ctx, destination)`，背后就是这一层

## 一、核心洞察：又一个注册表，而且是三张

v2ray 的扩展哲学一以贯之——**注册表 + init() 自注册**：

| 注册表 | 位置 | key → value | 注册者 |
|--------|------|-------------|--------|
| `transportDialerCache` | dialer.go:23 | 协议名 → `dialFunc` | 各传输协议包 init()，如 tcp/dialer.go:49 |
| `transportListenerCache` | tcp_hub.go:9 | 协议名 → `ListenFunc` | 各传输协议包 init()，如 tcp/hub.go:123、websocket/hub.go:183 |
| 全局 `typeCreatorRegistry` | common/type.go | **security engine 也用这张表** | tls/tls.go:74 注册 `*tls.Config` → Engine |

**TLS 不是传输协议，是"安全引擎"**——它以装饰器方式叠加在任意传输之上（tcp+tls / ws+tls / grpc+tls…），所以正交拆分。

第四个可替换点：`effectiveSystemDialer`（system_dialer.go:12）——真正发 syscall 的系统拨号器，全局变量可注入替换（测试、透明代理、VLite 等场景用）。

## 二、streamSettings：传输与安全正交的配置载体

```json
"streamSettings": {
  "network": "tcp",              // 传输层：tcp/ws/grpc/kcp/quic/httpupgrade…
  "security": "tls",             // 安全层：none/tls/utls/dtls…
  "tlsSettings": { "serverName": "example.com" },
  "tcpSettings": { "header": {...} }   // 传输层私有配置
}
```

protobuf 侧 `StreamConfig`（config.pb.go）→ `ToMemoryStreamConfig` 编译成 `MemoryStreamConfig`：
- `ProtocolName` + `ProtocolSettings`（传输层 typed 配置）
- `SecurityType` + `SecuritySettings`（安全层 typed 配置）
- `SocketSettings`（sockopt：TProxy/TOS/tcpKeepAlive 等）

取配置的回退链（config.go:91 GetTransportSettingsFor）：**per-stream → 全局 transport（已废弃）→ 该协议默认空配置**。

## 五、洋葱模型：层层包装的 net.Conn

每个包装层都实现 `net.Conn` 接口，所以对上层完全透明：

```
[应用流量] ⊂ [header 伪装] ⊂ [TLS] ⊂ [TCP/WS/gRPC 承载]
```

协议实现（vmess/vless/trojan）只看到一个"普通 conn"，完全不知道底下叠了几层——这正是"任何协议 × 任何传输 × 任何安全"自由组合的实现基础。

## 速记 + 自测

> **速记**：`Dial 查 dialer 表、Listen 查 listener 表，TLS 查的是全局表；洋葱包装层层实现 net.Conn；系统 dialer 是可注入的全局变量。`

1. 为什么 TLS 不做成一种"传输协议"（如 tls+tcp）而做成 security engine？
   （答：正交性——N 种传输 × M 种安全的组合只需 N+M 个实现，而非 N×M；tls 独立于 ws/grpc/tcp 复用。）
2. `getOriginalMessageName`（dialer.go:47）在搞什么？
   （答：proto option 里声明的"原始传输名"——允许新传输复用旧传输的 dialer（如 splithttp 类协议借道），配置名与实现名解耦。）
3. 入站 worker 拿到 conn 后到 socks.Process 之间发生了什么？
   （答：TLS Server 握手已在 accept 循环里完成；worker 包装 session.Inbound（来源/网关/用户），经 worker pool 分发，proxy 只管按 ctx 拿信息处理流量。）
