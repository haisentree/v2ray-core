## 一、嗅探器框架（sniffer.go）

### 五个内置嗅探器 + 一个可选组合器（NewSniffer:35）

| 嗅探器 | 网络 | 识别什么 | 实现位置 |
|--------|------|---------|---------|
| HTTP | TCP | 请求行/Host 头 | common/protocol/http |
| TLS | TCP | ClientHello 的 SNI | common/protocol/tls |
| QUIC | UDP | 初始包里的 SNI | common/protocol/quic |
| BitTorrent | TCP | BT 握手特征 | common/protocol/bittorrent |
| UTP | UDP | uTP 特征 | 同上 |
| **FakeDNS+others** | 全部 | 见下节 | fakednssniffer.go（配了 fakedns 才注册，且**插到列表最前**） |

每个嗅探器是 `protocolSnifferWithMetadata`：声明适用网络（TCP/UDP）+ 是否 metadata 型（连接建立时用 nil body 先跑一轮）。

### Sniff 状态机（:58-88，见上图左列）

每个嗅探器的错误是**协议化**的三态：
- `ErrNoClue`（"不认识这流量"）→ 挂入 pending，下轮换个顺序再试；
- `ErrProtoNeedMoreData`（"像，但数据不够"）→ **把嗅探器列表收缩为只剩它**（:73），下轮专注喂它——配合 default.go 外层的 200ms 总预算/最多 2 次；
- 成功 → 返回 `SniffResult{Protocol(), Domain()}`。

关键细节：**Sniffer 实例是每连接新建的**（default.go 的 `NewSniffer(ctx)`），列表收缩状态天然不跨连接泄漏——用"对象生命周期"代替"显式状态重置"。

### 结果合成（CompositeResult:117）

domain 与 protocol 可能来自不同嗅探器（fakedns 给域名、TLS 给协议名），合成 `compositeResult`；`ProtocolForDomainResult()` 让 02 课的 `shouldOverride` 能拿到"域名提供者"的协议名来判定是否改写目标。

## 二、FakeDNS：零成本的域名还原通道（fakednssniffer.go）

普通嗅探要**等首包**（TLS ClientHello 至少几百字节）；FakeDNS 不用——客户端当初问 DNS 时拿到的是假 IP，**IP 本身就是域名的编码**：

```
SniffMetadata（连接建立即调，body=nil）:
  fakeDNSEngine.GetDomainFromFakeDNS(target IP)
  → 命中：直接得到域名，0 字节嗅探，0 延迟
  → 未命中但 IP 在池内：可能 fakedns 重启丢了映射
     → 回退跑普通嗅探器，结果标 "fakedns+others"
  → IP 不在池内：正常走普通嗅探
```

工程细节彩蛋：`ipAddressInRange` ctx hack（:41-47,95）——fakedns 嗅探器和组合器之间没有参数通道，"IP 是否在池内"的判断结果通过 context 传值回传。**用 ctx 当隐式返回值**，整个文件唯一的"黑魔法"。

## 三、stats.go：25 行的装饰器

```go
type SizeStatWriter struct { Counter stats.Counter; Writer buf.Writer }
func (w *SizeStatWriter) WriteMultiBuffer(mb) error {
    w.Counter.Add(int64(mb.Len()))          // 计数
    return w.Writer.WriteMultiBuffer(mb)    // 透传
}
```

02 课 `getLink` 里挂的 `user>>>email>>>traffic>>>uplink` 就是它。**两处统计点位对比**：
- conn 级：worker 的 `StatCouterConnection`（proxyman/inbound 挂，统计整个入站）
- pipe 级：`SizeStatWriter`（dispatcher 挂，统计单个用户）
同一装饰器思想，两个粒度。

## 速记 + 自测

> **速记**：`嗅探器列表按网络过滤、三态错误驱动状态机、NeedMoreData 收缩列表、fakedns 走 metadata 通道零字节还原、结果合成看域名提供者`。

1. 为什么 `ErrProtoNeedMoreData` 要收缩列表而不是继续全量试？
   （答：某协议"匹配但需更多数据"意味着流量基本确定属于它——继续跑其他嗅探器只会浪费预算且可能误报；收缩是对"高置信度猜测"的资源倾斜。）
2. fakedns 嗅探为什么能不等首包？
   （答：域名在 DNS 查询阶段就编码进了假 IP，连接建立时只看目标地址即可反查——嗅探成本从"等 N 字节"降到"一次 map 查找"。）
3. 没配 fakedns 时 NewSniffer 会怎样？
   （答：newFakeDNSSniffer 返回 error → 两个 fakedns 相关嗅探器都不注册，列表只剩五个内容嗅探器——功能优雅降级，而非报错。）

## 五、番外：嗅探器怎么和 inbound 关联？数据怎么交互？

**答案：零直接调用，两条单向通道（见本课配图）。**

**控制面（开关的旅程）**：
```
JSON sniffing 段 → ReceiverConfig.SniffingSettings（v4 Build，01b 装配期）
→ worker 持有 sniffingConfig（always.go:121，07 课）
→ callback 写入 ctx：Content.SniffingRequest{Enabled, destOverride, MetadataOnly}（worker.go:89 ★交接点）
→ dispatcher.Dispatch 读开关（default.go:218）→ 决定起不起嗅探 goroutine
```

**数据面（首包的旅程）**：
```
客户端 payload → socks buf.Copy(reader, link.Writer) 写 uplink pipe（02 课）
→ cachedReader.Cache() 从 pipe 读出首包存 cache（default.go:36）——偷看，不消费
→ sniffer.Sniff(payload.Bytes()) → 08 课状态机
→ cache 在后续 ReadMultiBuffer 先吐出 → 数据一字节不丢，继续流向出站
```

三个关键认知：
1. **worker 从不给嗅探器喂连接**——它只把开关放进 ctx 就退场；数据是 dispatcher 自己从 pipe 里"偷"的。
2. **嗅探结果不回传 inbound**——`content.Protocol` 写回 ctx（日志用），改写的 dest 存 `session.Outbound`（路由用）。inbound 对结果永远无感知。
3. **inbound 是生产者，dispatcher 是消费者，嗅探器是旁观者**——三方职责用管道和 ctx 天然解耦，这就是为什么任何入站协议（socks/http/dokodemo）无需任何改动就能享受嗅探。
