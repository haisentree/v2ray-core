# 07 - 专题：app/proxyman/inbound 入站管理器解读

> 走读时间：2026-10-22
> 涉及文件：`inbound.go`(180 行) / `always.go`(187) / `dynamic.go`(203) / `worker.go`(528)
> 定位：补全 02 课一笔带过的 "Step 0"——从 accept 到 proxy.Process 之间发生的一切

## 一、三层结构（见上图）

```
Manager（feature 本体）
   └─ NewHandler 工厂（按 AllocationStrategy 分流）
        ├─ Always → AlwaysOnInboundHandler   ← 99% 的场景
        └─ Random → DynamicInboundHandler    ← 动态端口（遗留设计）
             └─ 1 个 proxy + N 个 worker
```

### 第 1 层：Manager（inbound.go:18）

最薄的一层，就是 `taggedHandlers map[string]inbound.Handler` + 增删启停。init() 注册两个类型（:173）——`*proxyman.InboundConfig`（Manager 自己）和 `*core.InboundHandlerConfig`（NewHandler 工厂），即 01b 讲的双注册。

### 第 2 层：NewHandler 工厂（inbound.go:139）

把 `InboundHandlerConfig` 拆成两半使用：`ReceiverSettings`（监听哪/嗅探/分配策略）+ `ProxySettings`（协议配置）。分流依据 `AllocationStrategy`：Always（默认）→ always.go；Random → dynamic.go。

### 第 3 层：AlwaysOnInboundHandler（always.go:51）—— "1 proxy + N workers"

创建过程四个关键动作：

1. `common.CreateObject(proxyConfig)`（:52）——**又查一次全局注册表**，把 `*socks.ServerConfig` 变成活的 socks Server（01b 三层注册表的第三层在此闭环）。
2. `p.Network()` 问协议"你支持哪些网络"（socks 回 TCP，udp:true 再加 UDP）。
3. 按 PortRange From..To × 支持的网络，**每个组合起一个 worker**（:108-145）。`port: 10808` 是单端口，配置写 `1000-2000` 就是一千个 tcpWorker。
4. `stats counter` 挂点（getStatCounter :19）：policy.ForSystem().Stats 开着才创建，名字格式 `inbound>>>tag>>>traffic>>>uplink`。

## 二、worker 三兄弟（worker.go）

| worker | 监听方式 | 核心差异 |
|--------|---------|---------|
| `tcpWorker`(:35) | `internet.ListenTCP`（04 课 listener 链） | 一 accept 一个 goroutine |
| `udpWorker`(:237) | `udp.ListenUDP` | **无连接 → 用 connID{src,dest} 模拟会话** |
| `dsWorker`(:439) | `internet.ListenUnix` | UDS 版 tcpWorker，同构 |

### tcpWorker.callback（:59）—— 02 课 Step 0 的真身

```go
ctx = session.ContextWithID(ctx, sid)                       // 会话 ID
ctx = session.ContextWithInbound(ctx, &session.Inbound{      // 来源/网关/tag
    Source: conn.RemoteAddr(), Gateway: ..., Tag: w.tag})
content.SniffingRequest.Enabled = sniffingConfig.Enabled     // 嗅探开关在这交接
ctx = session.ContextWithContent(ctx, content)
conn = &StatCouterConnection{...}                            // stats 计数装饰
w.proxy.Process(ctx, net.Network_TCP, conn, w.dispatcher)    // ★ 进入 02 课 Step 1
```

**彩蛋**：worker 的 dispatcher 不是直接给 routing dispatcher，而是 `h.mux`（mux.Server，always.go:120）——所有连接先进 mux server，非 mux 流量原样透传。这是为了 v1.mux.cool 复用连接时能就地解复用。

**透明代理支持**：`recvOrigDest`（:64）——tproxy/redirect 模式下从 conn 恢复原始目标地址塞进 ctx（dokodemo-door 场景），原始目的地不靠嗅探而靠内核。

### udpWorker 的"会话模拟"（:254-377）

UDP 没有连接概念，worker 用 `connID{src, dest}` 当 key 维护 `activeConn` map：
- 每个"会话"一根 **16KB pipe**（`DiscardOverflow()`，满了丢包不阻塞收包线程）；
- `task.Periodic` 每 16s 扫一遍，清掉 **8s 无活动**的会话（:363）；
- 同一 (src,dest) 的后续包直接复用已有会话 pipe——把无序报文流伪装成 conn，让 socks 的 UDP 处理代码完全复用 TCP 的写法。

### DynamicInboundHandler（dynamic.go）

`allocatePort()` 随机挑端口，`task.Periodic` 每 RefreshValue 分钟 `refresh()`：新开 Concurrency 个 worker → 等宽限期 → 关旧 worker。为动态端口对抗封锁设计的遗留功能，默认配置走不到。

## 三、串回主线

```
01b 装配: core.New → addInboundHandlers → Manager.AddHandler（此刻未监听）
02 数据: worker.callback = Step 0 真身；mux.Server 是隐形的第 0.5 步
04 传输: worker.Start → internet.ListenTCP → 查 transportListenerCache → tcp.ListenTCP
```

**一句话**：Manager 管 handler 生命周期，handler 把"一个协议 × 一个端口段"展开成 worker 集合，worker 守着 listener，把每次 accept 包装成带完整元数据的 ctx 调 `proxy.Process`——**协议实现从此可以完全不关心"连接从哪来"**。

## 四、番外：`New(ctx, config)` 的 config 为什么没用？

```protobuf
message InboundConfig {}   // proxyman/config.proto:14 —— 空 message
```

- `ConfigCreator` 统一签名 `func(ctx, config interface{}) (interface{}, error)`（common/type.go:11）：注册表是 `map[reflect.Type]ConfigCreator`，`CreateObject` 机械查表后 `creator(ctx, config)`。**若允许"有的 creator 不要 config"，调度器就得加分支**——统一签名换调度零逻辑。
- 空 message 的意义是**占位标记**：v4.Build() 无条件塞 `&proxyman.InboundConfig{}` 进 App 列表，语义即"请造一个 inbound manager，无可调参数"。类似 DI 框架里的空标签。
- Go 风格上本可写 `func New(ctx context.Context, _ *proxyman.InboundConfig)`，保留命名 `config` 纯为文档可读性；类型校验职责由 init() 注册处的断言承担。
- 同款：`&dispatcher.Config{}` 也是空 message；对照 `router.Config`（有 domainStrategy/rules 字段）就真用上了。

## 自测

1. 为什么 `port: "1000-2000"` 会创建 2001 个 tcpWorker 而不是一个 worker 监听端口段？
   （答：Go 的 net.Listener 一个 socket 只能绑一个端口；端口段场景（如 dokodemo 全端口透明代理）只能逐端口 worker。这也是 allocate.refresh 场景 worker 数量=concurrency 的原因。）
2. udpWorker 为什么要 DiscardOverflow 而 TCP worker 的 pipe 不需要？
   （答：UDP 丢包由上层协议容忍（重传/无序本就常态），收包线程绝不能被慢消费者阻塞——否则整个端口的包都停了；TCP 有内核缓冲背压。）
3. mux.Server 挡在 worker 和 dispatcher 之间，非 mux 流量会受影响吗？
   （答：不会，mux.Server 实现了 routing.Dispatcher 接口，非 mux 目标（非 v1.mux.cool）直接透传 Dispatch；只有 mux 目标才解复用。）
